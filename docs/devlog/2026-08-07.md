# 搭建日志 — 2026年8月7日

今天把「小零」工作台的文件夹从原来的 powershell 改成了正式的中文名「小零」，没想到这个简单的改名操作引发了一连串问题，花了不少时间才全部理顺。下面把整个过程和踩过的坑一一记录下来。

---

## 起因：文件夹改名

原本项目放在 D 盘根目录下的 powershell 文件夹里，这个名字是当初随手起的，跟项目完全没关系。今天决定把它改成正名「小零」。改名本身一秒钟就完成了，但桌面上的快捷方式集体失效——它们还指向着旧的路径，双击自然什么反应都没有。

这不只是快捷方式重建的问题，改名后整个项目的构建产物也跟着出了问题，需要从头梳理。

---

## 修复一：桌面快捷方式

之前的快捷方式指向的是 VBS 脚本，中间还经过一层 cmd 转发，路径又写死了文件夹名，改个名就全断了。这次干脆把快捷方式直接指向 Electron 的执行文件 electron.exe，参数传入主进程的入口脚本。这样路径清晰，少了一层中间跳转，以后维护也方便。创建快捷方式的脚本我写成了 Node.js 脚本 make-shortcut-electron.cjs，放在项目根目录，随时可以重新生成。

---

## 修复二：preload 脚本格式错误

快捷方式创建好之后，双击启动，电子窗口出现了但是空白一片。回头看终端报错：preload 脚本无法加载，提示不能在模块外使用 import 语句。

问题出在 Electron 对 preload 脚本的特殊要求。preload 运行在渲染进程的沙箱环境中，必须用 CommonJS 格式，而 electron-vite 的默认构建输出是 ESM 格式的文件。一个 index.mjs 文件被作为 preload 加载时，里面的 import 语句直接导致语法错误。

解决方法是修改 electron-vite 的构建配置，强制 preload 输出 CommonJS 格式，文件名也相应改为 index.cjs，主进程代码里引用 preload 的路径也要同步更新。这样一来 preload 加载成功，窗口才真正开始渲染内容。

---

## 修复三：数据库模块 ESM 兼容性问题

preload 修好后，应用开始启动时就崩溃了。报错信息指向 sql.js 初始化时试图给 undefined 设置 exports 属性。这是典型的 CommonJS 和 ESM 混用问题。项目的 package.json 里设置了 "type": "module"，整个项目被当作 ESM 处理。但 sql.js 是一个纯 CommonJS 包，它依赖运行时的 module.exports 对象来导出自己，在 ESM 环境下这个对象根本不存在。

解决思路分两步。第一步，在构建配置里把 sql.js 标记为外部模块，不让 Vite 把它打包进最终的 JS 文件里，这样它就保留原样从 node_modules 加载。第二步，在数据库模块中用 Node.js 的 createRequire 方法，创建一个 CommonJS 风格的 require 函数，专门用来加载 sql.js，这样它就能拿到正确的 module 对象了。

---

## 修复四：今日计划添加按钮无反应（核心问题）

这是今天踩得最深的一个坑。

现象很简单：打开今日计划页面，在输入框里打字，点击「添加」按钮，什么反应都没有，任务列表空空如也。代码逻辑看起来完全正确，handleAdd 函数检查输入是否为空，非空就调用 store 的 add 方法添加任务然后清空输入框。Zustand store 的 add 方法也很标准，用 crypto.randomUUID 生成 ID，拼一个任务对象塞进数组。

反复读代码、检查构建产物、确认 crypto API 可用，一切看起来都没问题。但问题就是不出来。

最终定位的根因出在 @base-ui/react 的 Input 组件上。Base UI 是一套无样式的 React 组件库，对标 Radix UI。它的 Input 组件实现受控模式时用的是 onValueChange 回调，接收两个参数：新的值和事件详情对象。而我们代码里传的是原生的 onChange 回调，接收的是一个事件对象，从里面取 target.value。

微妙之处在于，onChange 在 Base UI 的 Input 上确实存在（它继承自原生 HTML 属性），但它只是 DOM 级别的事件触发，不会驱动 Base UI 内部的受控状态同步机制。结果就是：用户在输入框里打字，浏览器显示文字正常，但 React 的 newTitle 状态始终为空字符串。handleAdd 里第一行就是 if (!newTitle.trim()) return，空字符串直接提前退出，后面的 add 永远不会被调用。整个链路断在了最不起眼的地方。

修复方式是在我自己封装的 Input 组件里加一层适配，把外部的 onChange 回调转成 Base UI 需要的 onValueChange 格式。当 onValueChange 触发时，拿到的是纯字符串值，手动构造一个形如 { target: { value: 字符串 } } 的对象传给原来的 onChange 回调。代码改动只有三行，但定位这个 bug 花了一个多小时。

这个坑给我的教训是：使用第三方 headless 组件库时，不能想当然地认为它跟原生 HTML 元素 API 完全一致。特别是 Input 这种高频使用的组件，受控和非受控的同步机制往往封装了额外的逻辑。Base UI 用 onValueChange 而不是 onChange 来驱动受控状态，官方文档里虽然写了，但如果不仔细看很容易用错。最坑的是用错了不会报错，UI 看起来正常，就是数据不流通。

## 修复五：ServiceWorker 注册报错

Electron 用 file 协议加载本地的前端页面，但页面里有一段 PWA 的 ServiceWorker 注册代码。file 协议下 ServiceWorker 是不可用的，所以每次启动都会在控制台留下一条报错。不算 bug，但刷屏比较烦。给注册语句后面加了个空的 catch 回调，报错就静默吞掉了。
